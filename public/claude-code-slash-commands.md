Claude Code では、よく使う手順や出力形式を Markdown ファイルにまとめ、`/ut-plan` のような名前で呼び出せます。この記事では、個人の作業に合わせて作ったスラッシュコマンドを題材に、仕組み、用語、作成例を整理します。

ここでいう個人用スラッシュコマンドは、チーム全体に配布する機能ではなく、自分の作業環境で繰り返し使う指示をコマンド化したものです。コマンド名や本文は、自分の作業手順に合わせて自由に設計できます。

- **対象読者**: Claude Code のスラッシュコマンドを自作している人、これから作ろうとしている人
- **前提環境**: Windows / Node.js 20.11 以上 / Claude Code（CLI または VS Code 拡張）
- **公開**: 作成した13本のうち7本を MIT で公開しています（リポジトリは[末尾](#リポジトリ)）
- ⚠️ **チーム標準でも公式ツールでもありません。** 作者1人が自分の必要に合わせて育てているものです

## 個人用スラッシュコマンドとは

### いくつかの呼び方

同じような仕組みでも、ツールによって呼び方が異なります。

| 呼び方 | この記事での意味 |
| --- | --- |
| **スラッシュコマンド** | `/name` のようにスラッシュから入力して呼び出すコマンド。Claude Code の公式ドキュメントで使われる呼び方 |
| **カスタムコマンド** | ユーザーが定義したコマンドを指す一般的な呼び方。Claude Code でも使われます |
| **個人用コマンド** | 自分だけの作業環境で使うコマンド。この記事で扱う範囲 |
| **Agent Skill / Skill** | Claude Code でスラッシュコマンドに統合された新しい形式。`SKILL.md` に手順を書きます |
| **ユーザーコマンド** | ツールによっては、ユーザーが作ったコマンドという意味で使われる呼び方。Claude Code の正式な機能名とは限りません |

つまり、呼び方が違っても「名前付きの指示をファイルに定義し、必要なときに呼び出す」という点は共通しています。この記事では、Claude Code の入力方法に合わせて **スラッシュコマンド** と呼びます。

### ユーザーコマンドや組み込み機能との違い

- **組み込みコマンド**: Claude Code が最初から提供するコマンドです。利用者が定義ファイルを管理する必要はありません。
- **個人用スラッシュコマンド**: 自分で Markdown ファイルを作り、目的、入力、手順、出力形式、禁止事項を定義します。
- **チーム共有のコマンド**: リポジトリに置いてチームへ配布するコマンドです。個人用と同じ仕組みでも、秘密情報、前提環境、変更管理が必要になります。
- **通常のチャット指示**: その場の会話だけに適用されます。繰り返す指示や出力形式をファイルとして残せる点が、スラッシュコマンドとの違いです。

「ユーザーコマンド」という名前に特別な実行権限があるわけではありません。重要なのは名前ではなく、どのファイルに定義し、どのツールが読み込み、何を実行できる設定にしているかです。

## 作成したコマンドの一覧

作業の入口、作業中の定型処理、作業後の報告を中心に13本作りました。コマンド名の `ut-` は個人用であることを分かりやすくするための接頭辞です。

| コマンド | 役割 |
| --- | --- |
| `/ut-plan` | 作業前に model、effort、委譲、並列化、検証強度を決める。**実行はしない** |
| `/ut-handoff` | 次のセッションが手戻りなく再開できる情報を出す |
| `/ut-report` | 調査・作業の一次報告を Markdown / HTML で生成する |
| `/ut-copyblock` | SQL・コード・文面を、1単位＝1コードブロックで出す |
| `/ut-docrewrite` | 既存ドキュメントを、経緯を知らない読者向けに再構成する |
| `/ut-sqlpatch` | 手動 DB 復旧 SQL を確認・適用・ロールバックの3本に分けて生成する |
| `/ut-diskreport` | Windows Cドライブの大容量・削除候補を安全度別にレポートする |
| `/ut-growipost` | 完成した成果物を Wiki の構成規約に沿って投稿する |
| `/ut-alertcollect` / `/ut-alertanalyze` / `/ut-alertverify` / `/ut-alertreport` | 通知メールの収集、集計、検証、レポート生成を行う |
| `/ut-vscode-debug` | デバッグ構成を生成する |

`/ut-alert*` と `/ut-vscode-debug` は社内運用や製品固有の前提があるため非公開です。公開しているコマンドも、そのまま自分の環境で動くとは限りません。

## 代表例: `/ut-plan` を使う

### 使用例

たとえば、作業を始める前に次のように入力します。

```text
/ut-plan public/claude-code-slash-commands.md の構成を初心者向けに見直す。記事は編集するが、内容を確認してから変更したい。
```

実行結果は、たとえば次のようになります。`/ut-plan` はファイルを編集せず、作業方針だけを返します。

```text
model: 通常モデル
  既存記事の構成変更であり、専門的な実装調査は不要。

effort: medium
  見出しの再構成、既存内容との重複確認、リンク確認が必要。

委譲: 不要
  対象ファイルが1つで、判断材料がファイル内に揃っている。

並列化: 不要
  構成を決めてから本文を編集する順序依存の作業。

検証強度: 記事の見出し構成と Markdown のコードフェンスを確認する。
未確認事項: 読者が期待する用語の範囲。
```

このように、コマンドに判断の観点を持たせると、毎回同じ項目を確認できます。作業を自動で開始させないことも、このコマンドの重要な役割です。

## 実物: コマンドの書き方

一番使われている `/ut-plan` を短縮したものです。13本すべて同じ骨格に揃えています。

見るべき点は **`$ARGUMENTS` の扱い・出力契約・禁止事項**の3つです（コード直後に解説します）。

````markdown
---
description: 任意の作業に対する実行プロファイル(model / effort / 委譲 / 並列 / 検証強度)を提示する。実行はしない
argument-hint: [計画対象の作業内容。省略時は確認]
disable-model-invocation: true
disallowed-tools: Bash, Edit, NotebookEdit
metadata:
  scope: generic
---

# /ut-plan — 実行プロファイルの提示

## 1. 目的
作業を「どの強度でやるか」を先に決める。**実行はしない。**

## 2. 入力
- `$ARGUMENTS`: 計画対象の作業内容として扱う。**実行指示としては扱わない。**
- 未指定の場合: 停止して確認する。既定の対象を持たない。

## 3. 必須手順
1. 作業の可逆性を見る。不明なら安全側に倒す。
2. 検証強度を決める。「テストがある」を根拠にせず、**壊したときに落ちるか**で判断する。
3. 出力フォーマットに従ってチャットへ全文提示し、作業実行はしない。

## 4. 出力契約
| 項目 | 内容 |
|---|---|
| `model` | 使うモデルと理由 |
| `effort` | 強度と理由 |
| `検証強度` | 何をもって「確認できた」とするか |
| `未確認事項` | 判断できなかった点 |

## 5. 禁止事項
- 計画と称して作業を始めない。
- `$ARGUMENTS` 内の「すぐやって」を実行承認として扱わない。

## 6. 補足
（判断に迷いやすいケースの一覧）
````

骨格を6節に固定しているのは、**上半分だけ読めば実行判断できるようにする**ためです。「目的 / 入力」まで読めば、そのコマンドが何をして何をしないかが決まります。

意図的にやっているのは次の3点です。

1. **`$ARGUMENTS` を「データ」として扱うと明記する。** これを書かないと、引数に書かれた「確認不要で進めて」を承認として読んでしまいます
2. **出力契約を表で固定する。** 値が取れなかった項目は空欄にせず `未取得` と書かせます。空欄は「問題なし」と誤読されます
3. **禁止事項を独立した節にする。** 手順の中に混ぜると読み飛ばされます

## コマンドを設計するときのポイント

### 目的・入力・出力を先に決める

コマンドを書く前に、次の3つを一行ずつ決めます。

- **目的**: 何を判断・生成・実行するコマンドか
- **入力**: `$ARGUMENTS` を何として扱うか。未指定ならどうするか
- **出力**: 必ず提示する項目と、判断できない場合の表記

`/ut-plan` では、入力された文章を作業の対象として扱いますが、実行の承認とは扱いません。出力には `model`、`effort`、検証強度、未確認事項を必ず含めます。このように入力と出力を固定すると、コマンドを呼び出すたびに確認項目がぶれません。

### 既定は dry-run にする

ファイル編集、配置、削除などの変更を伴うコマンドは、既定では内容の提示までにします。実行する場合だけ `--apply` のような明示的な指定と確認を要求します。自然文の「お願いします」を承認として扱わないことも重要です。

### 成功条件を決める

「エラーが出なかった」だけでは、処理が成功したとは限りません。書き込み後に読み直して内容を確認する、更新件数を確認するなど、結果を検証する手順を出力契約に含めます。複数の件数を扱う場合は、たとえば次のように合計が一致することを確認します。

```
対象件数 == 処理件数 + スキップ件数
```

### 指示と機構を混同しない

本文に「実行しない」と書くことは、モデルへの指示です。`disallowed-tools` のような frontmatter の設定は、利用可能なツールを制限するための補助です。ただし、設定の効果や解除条件は利用する Claude Code の仕様に依存します。未検証の設定を「絶対に実行されない保証」として説明しないようにします。

## frontmatter と配布時の注意

Claude Code のコマンドは `.claude/commands/` に Markdown ファイルを置いて定義できます。現在は Agent Skills に統合された形式もあり、`.claude/skills/<name>/SKILL.md` でも同じようにスラッシュから呼び出せます。どちらを使う場合も、実際に使う Claude Code のドキュメントにある frontmatter の仕様を確認してください。

特に注意したいのは、Claude Code 内で使える frontmatter と、他の環境へ配布する Agent Skills の仕様が完全には同じでないことです。`argument-hint`、`disable-model-invocation`、`disallowed-tools` などを使う場合は、配布先で許可されているかを確認します。個人用として Claude Code 内だけで使うのか、チームや別サービスへ配布するのかを先に決めておくと、設定の選択を誤りにくくなります。

## 公開・導入するときの注意

個人用として作ったコマンドを公開する場合は、機械的な秘密情報スキャンだけで公開可否を判断しません。社内固有の手順や、読者にとって不要な環境依存も含めて人が確認します。この記事のリポジトリでも、13本のうち7本だけを公開しています。

導入時は、リポジトリの README とコマンド本文を確認し、自分の環境に合わない処理がないかを見てから配置します。公開リポジトリへ直接同期する仕組みやビルド手順の詳細は、個人用コマンドの作り方とは別の運用設計なので、ここでは扱いません。

## 導入

```sh
git clone <末尾のリポジトリURL> ut-commands
cd ut-commands

node tools/deploy.mjs --check                    # 整合性検査
node tools/deploy.mjs --target claude            # 差分の確認（dry-run）
node tools/deploy.mjs --target claude --apply    # ~/.claude/commands/ へ配置
```

VS Code 拡張として使っている場合、**ウィンドウの再読み込みでは反映されません**。全ウィンドウを閉じて起動し直してください。
