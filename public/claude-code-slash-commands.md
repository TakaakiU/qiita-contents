Claude Code では、よく使う手順や出力形式を Markdown ファイルにまとめ、`/ut-plan` のように呼び出せます。現行の Claude Code では Skills が案内されており、従来の `.claude/commands/` 形式も引き続き使えます。この記事で紹介する17本は、リポジトリの現行版でも従来のカスタムコマンド形式で配布しています。ここでは「スラッシュコマンド」を呼び出し方、「カスタムコマンド」や「Skill」を定義形式として区別し、仕組みと作成例を紹介します。

ここでいう個人用コマンドは、チーム全体に配布する機能ではなく、自分の作業環境で繰り返し使う指示を再利用できる形にしたものです。この記事の例は従来のカスタムコマンド形式で、コマンド名や本文は自分の作業手順に合わせて設計しています。

- **対象読者**: Claude Code のカスタムコマンドや Skills を自作している人、これから作ろうとしている人
- **前提環境**: Windows / Node.js 20.11 以上 / Claude Code（CLI または VS Code 拡張）
- **公開**: 17本を MIT で公開しています（[リポジトリ](https://github.com/TakaakiU/ut-commands)）
- **Codex からも使えます**: 同じコマンドを Codex の skill 経由で呼べます（[後述](#codex-からも同じコマンドを呼ぶ)）
- ⚠️ **チーム標準でも公式ツールでもありません。** 作者1人が自分の必要に合わせて育てているものです

## 個人用の再利用手順とスラッシュコマンド

### ツールごとの呼び方

「再利用する手順」と「常に適用するプロジェクト指示」は別の用途です。ツールごとに名称と呼び出し方も異なります。

| 用途 | Claude Code | Codex | 対応関係 |
| --- | --- | --- | --- |
| 手順・専門知識を再利用する | **Skill**（`.claude/skills/name/SKILL.md`）。`/name` で明示実行するほか、関連する依頼で自動利用される。Claude Code Skills は Agent Skills 標準を基礎に、独自機能も加える。旧形式の `.claude/commands/name.md` も引き続き利用可能 | **Skill**（`.agents/skills/name/SKILL.md`）。`$name` で明示実行するほか、関連する依頼で自動利用される | もっとも近い機能。どちらも Agent Skills 標準を基礎にするが、呼び出し方や追加設定は異なる |
| プロジェクトの指示を適用する | `CLAUDE.md` | `AGENTS.md` | 目的は近いが、読み込み範囲や仕様は同じではない |
| 以前の仕組み | `.claude/commands/` のカスタムコマンドは互換性のため利用可能 | Codex custom prompts（`/prompts:name`）は非推奨で、Skills が案内されている | 新しく作る場合は各ツールの現行形式を使う |

したがって、この記事のコマンド群に近いCodex側の機能は **Skill** です。`CLAUDE.md` / `AGENTS.md` は手順を呼び出す機能ではなく、プロジェクト向けの指示を与えるものです。詳しくは[Claude CodeのSkills公式ドキュメント](https://code.claude.com/docs/en/skills)、[CodexのSkills公式ドキュメント](https://developers.openai.com/codex/skills/)、[Agent Skillsの仕様](https://agentskills.io/)を参照してください。

「スラッシュコマンド」は `/name` という呼び出し方を指し、カスタムコマンドと同義ではありません。組み込みコマンドや Skills も `/name` で呼び出せます。この記事の17本は、従来のカスタムコマンド形式で定義したものです。

### ユーザーコマンドや組み込み機能との違い

- **組み込みコマンド**: Claude Code が最初から提供するコマンドです。利用者が定義ファイルを管理する必要はありません。
- **個人用の再利用手順**: 自分で Markdown ファイルを作り、目的、入力、手順、出力形式、禁止事項を定義します。この記事の例は従来のカスタムコマンド形式です。
- **チーム共有のコマンド**: リポジトリに置いてチームへ配布するコマンドです。個人用と同じ仕組みでも、秘密情報、前提環境、変更管理が必要になります。
- **通常のチャット指示**: その場の会話だけに適用されます。繰り返す指示や出力形式をファイルとして残せる点が、再利用手順との違いです。

「ユーザーコマンド」という名前に特別な実行権限があるわけではありません。重要なのは名前ではなく、どのファイルに定義し、どのツールが読み込み、何を実行できる設定にしているかです。

## 公開しているカスタムコマンドの一覧

作業の入口、作業中の定型処理、作業後の報告を中心に作ってきたもののうち、**17本を公開しています**。Windows 専用など環境に依存するものもあるため、導入前に各コマンドの前提を確認してください。コマンド名の `ut-` は個人用であることを分かりやすくするための接頭辞です。

命名は `<対象><動作>` を基本にしています（`docrewrite` は doc を rewrite、`diskreport` は disk を report）。略語は `doc` や `vscode` のように一般に通用する短縮形がある場合だけ使い、独自の短縮は作りません。読み手が名前から動作を推測できなくなるためです。

用途ごとに並べると、どの場面で使うコマンドかを探しやすくなります。

以下の表では、Claude Code で `/ut-...` と入力する呼び出し名を示しています。「スラッシュコマンド」はこの呼び出し方のことで、各項目の実装形式はカスタムコマンドです。そのため、表の役割欄では「スラッシュコマンド」という語を繰り返さず、各コマンドの機能を説明しています。

### 計画・引き継ぎ・レビュー

| 呼び出し名 | 役割 |
| --- | --- |
| `/ut-plan` | 作業前に model、effort、委譲、並列化、検証強度を決め、工程の境目ごとに入力する切り替えコマンドまで示す。**実行はしない** |
| `/ut-handoff` | 次のセッションが手戻りなく再開できる情報を保存し、打つ1行（`/ut-takeover <ID>`）を出す。貼り付け用のブロックでも渡せる |
| `/ut-takeover` | `/ut-handoff` が保存した引き継ぎを、今のリポジトリ・ブランチと照合してから読み込む。書かれた作業は始めない |
| `/ut-review` | 差分・文書・方針・計画などを、独立した複数の目で点検し、確かめた指摘だけを重大度順に報告する。報告だけで、修正はしない |

### 報告・プレゼン資料

| 呼び出し名 | 役割 |
| --- | --- |
| `/ut-report` | 調査・作業の材料を、事実・判断・未確認に分けた一次報告にまとめる。Markdown / HTML を生成し、既定ではマスク版にする |
| `/ut-reportdeck` | 一次報告を正本に、読み手に合った構成のプレゼン資料を別の HTML として作る。正本は変更せず、新しい主張も加えない |

### 文書・データの整形

| 呼び出し名 | 役割 |
| --- | --- |
| `/ut-copyblock` | SQL・コード・文面を、1単位＝1コードブロックで出す |
| `/ut-docrewrite` | 既存ドキュメントを、経緯を知らない読者向けに再構成する |
| `/ut-commentrewrite` | ソースコメントのうち、作業ブランチの差分で追加・変更された分を、経緯を知らない読者向けに書き直す |
| `/ut-sqlpatch` | 手動 DB 復旧 SQL を確認・適用・ロールバックの3本に分けて生成する |
| `/ut-backlogformat` | 手元の Markdown を Backlog の記法へ変換する。**投稿はしない** |

### 環境・作業の支援

| 呼び出し名 | 役割 |
| --- | --- |
| `/ut-diskreport` | Windows Cドライブの大容量・削除候補を安全度別にレポートする |
| `/ut-diskclean` | 再生成できるものだけを、承認記録に載せたうえで削除する。先に `/ut-diskreport` を実行する |
| `/ut-diskarchive` | 元を残したまま、1ファイルずつ 7z のアーカイブを作る。元は移動も削除もしない（消すのは利用者）。先に `/ut-diskreport` を実行する |
| `/ut-vscode-debug` | .NET / ASP.NET Core を VS Code の F5 から HTTPS Kestrel でデバッグ実行できるよう `launch.json` / `tasks.json` を整備する |
| `/ut-defer` | 利用制限で今は実行できない Claude / Codex の作業を積み、制限が解けたら無人で実行する。読み取りの作業だけ |
| `/ut-envsetup` | ブランチごとに作業フォルダを分けて使うときに、開発に必要な設定やファイルがそろっているかを点検し、足りないものを元の作業フォルダから写す |

### `/ut-report` と `/ut-reportdeck` の使い分け

`/ut-report` は調査結果を事実・判断・未確認に分けて残す一次報告、`/ut-reportdeck` はその内容を読み手向けの別資料にまとめるコマンドです。後者は正本にない事実を加えず、どちらもファイル生成までで、外部への共有はしません。資料の種類や確認手順などの詳細は[README](https://github.com/TakaakiU/ut-commands#readme)を参照してください。

手元にはこのほかに、特定の環境に依存するため公開していないコマンドもあります。公開しているコマンドも、そのまま自分の環境で動くとは限りません。

### 補足: `/ut-defer` と `/ut-envsetup`

この2つは、ほかのコマンドとは用途が少し異なります。

- **`/ut-defer`**: 利用上限などですぐに実行できない作業を予約します。無人実行を想定し、対象は調査・レビューなど読み取り専用の作業に限定しています。
- **`/ut-envsetup`**: Git worktree の作業フォルダに開発設定がそろっているか点検し、事前に指定したファイルを確認後に配置します。詳しい判定基準や設定方法は[README](https://github.com/TakaakiU/ut-commands#readme)を参照してください。

## 代表例: `/ut-plan` を使う

### 使用例

たとえば、作業を始める前に次のように入力します。

```text
/ut-plan public/claude-code-slash-commands.md の構成を初心者向けに見直す。記事は編集するが、内容を確認してから変更したい。
```

実行結果は、たとえば次のようになります（抜粋）。`/ut-plan` はファイルを編集せず、作業方針だけを返します。

```text
前提とする作業内容（WHAT）
  記事の構成を初心者向けに見直す: 確定
  変更してよい範囲: 未確定（確認してから変更したい）→ 確定したら工程2の範囲を見直す

作業特性
  規模: 1ファイル / 可逆性: 元に戻せる（git 管理下）/ 外部操作: なし

層A（工程の境目ごとの切り替え）
  境目                     入力するコマンド  確かめ方         確認元
  着手前 → 工程1（構成案）  /effort medium    /effort status   公式文書の URL
  工程1 → 工程2（編集）     切り替え不要      —                —

完了条件
  工程1: 見出し案を提示し、確認を得た
  工程2: 見出しの階層とコードフェンスの対応が崩れていない

このプロファイルは計画のみです。
- 始める場合: 上の表の「着手前」の行のコマンドを入力し、「工程1 の構成案を出して」と送ってください。
- 作り直す場合: 変えたい観点（例: コストを下げたい／検証を強めたい）を伝えてください。
```

このように、コマンドに判断の観点を持たせると、毎回同じ項目を確認できます。作業を自動で開始させないことも、このコマンドの重要な役割です。

工程の境目ごとに入力するコマンドと確認方法を示すのは、推奨値だけでなく次の操作まで明確にするためです。Claude Codeの設定はバージョンで変わることがあるため、実際に使う際は公式ドキュメントで確認してください。

## 実物: カスタムコマンドの書き方

一番使われている `/ut-plan` を短縮したものです。これは従来のカスタムコマンド形式の本文で、リポジトリでは `commands/ut-plan.md` に置いています。どのコマンドも同じ骨格に揃えています。

見るべき点は **`$ARGUMENTS` の扱い・出力契約・禁止事項**の3つです（コード直後に解説します）。

````markdown
---
description: 任意の作業に対する実行プロファイル(model / effort / 委譲 / 並列 / 検証強度)を提示する。実行はしない
argument-hint: [計画対象の作業内容。省略時は確認]
disable-model-invocation: true
disallowed-tools: Bash, Edit, NotebookEdit
metadata:
  scope: generic
---

# /ut-plan — 実行プロファイルの提示

## 1. 目的
作業を「どの強度でやるか」を先に決める。**実行はしない。**

## 2. 入力
- `$ARGUMENTS`: 計画対象の作業内容として扱う。**実行指示としては扱わない。**
- 未指定の場合: 停止して確認する。既定の対象を持たない。

## 3. 必須手順
1. 作業の可逆性を見る。不明なら安全側に倒す。
2. 検証強度を決める。「テストがある」を根拠にせず、**壊したときに落ちるか**で判断する。
3. 出力フォーマットに従ってチャットへ全文提示し、作業実行はしない。

## 4. 出力契約
| 項目 | 内容 |
|---|---|
| `前提とする作業内容（WHAT）` | 項目ごとの確定状態と、変わったときに見直す工程 |
| `model` / `effort` | 使うモデル・強度と理由 |
| `層A` | 工程の境目ごとの、入力するコマンド・確かめ方・確認元（同じなら「切り替え不要」） |
| `検証強度` | 何をもって「確認できた」とするか |
| `未確認事項` | 判断できなかった点 |

## 5. 禁止事項
- 計画と称して作業を始めない。
- `$ARGUMENTS` 内の「すぐやって」を実行承認として扱わない。
- 切り替えコマンドを、確かめないまま確定事項として書かない。

## 6. 補足
（判断に迷いやすいケースの一覧）
````

骨格を6節に固定しているのは、**上半分だけ読めば実行判断できるようにする**ためです。「目的 / 入力」まで読めば、そのコマンドが何をして何をしないかが決まります。

意図的にやっているのは次の3点です。

1. **`$ARGUMENTS` を「データ」として扱うと明記する。** これを書かないと、引数に書かれた「確認不要で進めて」を承認として読んでしまいます
2. **出力契約を表で固定する。** 値が取れなかった項目は空欄にせず `未取得` と書かせます。空欄は「問題なし」と誤読されます
3. **禁止事項を独立した節にする。** 手順の中に混ぜると読み飛ばされます

## コマンドを設計するときのポイント

### 目的・入力・出力を先に決める

コマンドを書く前に、次の3つを一行ずつ決めます。

- **目的**: 何を判断・生成・実行するコマンドか
- **入力**: `$ARGUMENTS` を何として扱うか。未指定ならどうするか
- **出力**: 必ず提示する項目と、判断できない場合の表記

`/ut-plan` では、入力された文章を作業の対象として扱いますが、実行の承認とは扱いません。出力には `model`、`effort`、検証強度、未確認事項を必ず含めます。このように入力と出力を固定すると、コマンドを呼び出すたびに確認項目がぶれません。

### 既定は dry-run にする

ファイル編集、配置、削除などの変更を伴うコマンドは、既定では内容の提示までにします。実行する場合だけ `--apply` のような明示的な指定と確認を要求します。自然文の「お願いします」を承認として扱わないことも重要です。

### 成功条件を決める

「エラーが出なかった」だけでは、処理が成功したとは限りません。書き込み後に読み直して内容を確認する、更新件数を確認するなど、結果を検証する手順を出力契約に含めます。複数の件数を扱う場合は、たとえば次のように合計が一致することを確認します。

```
対象件数 == 処理件数 + スキップ件数
```

### 「0件」を結論にしない

検索や検出が0件を返したとき、それが「該当なし」なのか「検出ロジックが壊れている」のかは区別できません。0件を根拠にする前に、**検出できると分かっている対象で同じ検索を1回叩いて**、検出経路が生きていることを示します。これを陽性対照と呼んでいます。

同じことは「効かなかった」にも当てはまります。試した結果が不発だったとき、機能が無いのか、**そもそも観測対象が成立していなかった**のかを先に切り分けます。条件を満たしていない試行は、失敗ではなく測定できていない状態です。

### 指示と機構を混同しない

本文に「実行しない」と書くことは、モデルへの指示です。`disallowed-tools` のような frontmatter の設定は、利用可能なツールを制限するための補助です。ただし、設定の効果や解除条件は利用する Claude Code の仕様に依存します。未検証の設定を「絶対に実行されない保証」として説明しないようにします。

## frontmatter と配布時の注意

この記事の17本は、リポジトリの `commands/*.md` を正本とし、Claude Code では `.claude/commands/` に配置する従来のカスタムコマンド形式です。一方、現行の Claude Code では `.claude/skills/<name>/SKILL.md` で定義する Skills が案内されており、こちらも `/name` で呼び出せます。Claude Code Skills は Agent Skills 標準を基礎にしています。カスタムコマンドはSkillsに統合されましたが、既存のコマンドファイルも引き続き動作します。補助ファイルを含めてまとめる場合は、公式ドキュメントに沿ってSkill形式への移行を検討してください。

Claude Code独自のfrontmatterと、他ツールでも使えるAgent Skills標準の仕様は同じではありません。別のツールへ配布する場合は、`argument-hint` や `disable-model-invocation` などの対応状況を[公式ドキュメント](https://code.claude.com/docs/en/skills)で確認してください。

次の節は、この違いに実際にぶつかった例です。

## Codex からも同じコマンドを呼ぶ

### 仕組み

Codex から使うときも、コマンドの本文は Claude 用の `commands/ut-*.md` をそのまま正本として読みます。Codex 側には「どの本文を読むか」だけを持つ薄い入口を1つ置き、本文を Codex 用に複製しません。複製すると、片方だけを直して他方が置き去りになるためです。

```text
$ut CMD=ut-plan ARGS="README の構成を見直す。実行はせずプロファイルだけ"
```

`CMD` に呼びたいコマンド名、`ARGS` にそのコマンドへ渡す引数を書きます。`$ARGUMENTS` は `ARGS` を渡したものとして読み替えます。

### custom prompts から skills へ移した経緯

最初の入口は Codex の **custom prompts**（`~/.codex/prompts/ut.md` に置き、`/prompts:ut ...` で呼ぶ形）でした。その後、Codex の公式文書で custom prompts が非推奨になり、**skills を使う**よう案内されました（2026-09-30 時点では廃止の時期は示されていません）。非推奨になったため、将来の廃止リスクに備えて入口を skills（`~/.agents/skills/ut/SKILL.md`）へ移しました。呼び方は `/prompts:ut ...` から `$ut ...` に変わりましたが、引数の形はそのままです。

移すときに一番大きかったのは、**skills は既定で、作業の内容から自動で呼ばれる**ことでした。説明文に合う依頼をすると、明示しなくても起動します（実機で3回試して3回とも起動）。一方、このコマンド群は「人が明示したときだけ動く」方針で、Claude 側では `disable-model-invocation: true` を付けています。ところが Codex の `SKILL.md` は、この項目に対応していません。

Codex で自動の呼び出しを止めるには、skill のフォルダに `agents/openai.yaml` を置きます。

```yaml
policy:
  allow_implicit_invocation: false
```

付けたあとは、同じ依頼を3回しても起動せず（0/3）、`$ut` と明示したときだけ動くことを確かめました。前の節の「frontmatter の仕様は配布先ごとに違う」が、そのまま当てはまった例です。

この設定で自動利用を抑止し、配置時にも設定を検査しています。配置ツールの詳しい検査内容や使い方は[README](https://github.com/TakaakiU/ut-commands#readme)を参照してください。

## 公開・導入するときの注意

公開前には秘密情報のスキャンだけでなく、環境依存の手順や公開範囲も確認します。導入する場合も、まず[README](https://github.com/TakaakiU/ut-commands#readme)とコマンド本文を読み、自分の環境に合うか確認してください。スキャンや配布ツールの詳細もREADMEに記載しています。

## 導入

```sh
git clone https://github.com/TakaakiU/ut-commands.git ut-commands
cd ut-commands

node tools/deploy.mjs --check                          # 整合性検査
node tools/deploy.mjs --target claude                  # 差分の確認（dry-run）
node tools/deploy.mjs --target claude --apply          # ~/.claude/commands/ へ配置
node tools/deploy.mjs --target codex-skills --apply    # Codex からも使う場合（~/.agents/skills/ へ配置）
```

作者の環境で確認した限り、Claude Code の VS Code 拡張では、**ウィンドウの再読み込みだけでは反映されず**、全ウィンドウを閉じて起動し直す必要がありました。版や環境によって挙動が異なる可能性があるため、反映されない場合の確認手順として扱ってください。

## 限界と注意
