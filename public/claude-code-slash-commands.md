Claude Code では、何度も使う作業手順を Markdown ファイルに書いておき、`/ut-plan` のように呼び出せます。このように `/名前` の形で呼び出す方法を「スラッシュコマンド」と呼びます。毎回同じ説明を入力しなくてよくなるため、決まった手順で作業したいときに便利です。

Claude Code では、新しい形式として Skills（スキル）が案内されていますが、以前からある `.claude/commands/` 形式も引き続き使えます。この記事で紹介する17本は、後者の形式で作ったものです。`/名前` は呼び出し方、カスタムコマンドや Skill は手順を書いておくファイルの形式、と考えてください。この記事ではその違いと、作り方の例を紹介します。

この記事のコマンドは、チーム全員に配るためのものではなく、作者自身が何度も使う手順をファイルにまとめたものです。

- **対象読者**: Claude Code のカスタムコマンドや Skills を自作している人、これから作ろうとしている人
- **前提環境**: Windows / Node.js 20.11 以上 / Claude Code（コマンドライン版（CLI）または VS Code 拡張）
- **公開**: 17本を MIT で公開しています（[リポジトリ](https://github.com/TakaakiU/ut-commands)）
- **Codex からも使えます**: 同じコマンドを Codex の skill 経由で呼べます（[後述](#codex-からも同じコマンドを呼ぶ)）
- ⚠️ **チーム標準でも公式ツールでもありません。** 作者1人が自分の必要に合わせて育てているものです

## 個人用の作業手順とスラッシュコマンド

ここでは、似ている2つの仕組みを分けて説明します。

- **必要なときに呼び出す手順**: たとえば「作業前に計画を立てる」手順を、使いたいときに呼び出します。
- **プロジェクトでいつも参照する指示**: たとえば「このプロジェクトではこのテストを実行する」といった前提やルールを、作業中に参照させます。

前者は必要な作業を始めるためのレシピ、後者はそのプロジェクトで作業するときの共通ルールです。

### ツールごとの呼び方

「使いたいときに呼び出す作業手順」と「そのプロジェクトで作業するときに参照する共通ルール」は、別の仕組みです。ツールによって名前や使い方も異なります。

| やりたいこと | Claude Code | Codex | ひとことで言うと |
| --- | --- | --- | --- |
| 必要なときに手順を呼び出す | **Skill**（`.claude/skills/name/SKILL.md`）。`/name` と入力して呼び出せます。依頼内容に応じて自動で使われる場合もあります。以前の `.claude/commands/name.md` 形式も使えます | **Skill**（`.agents/skills/name/SKILL.md`）。`$name` と入力して呼び出せます。依頼内容に応じて自動で使われる場合もあります | どちらも、作業の手順をファイルに書いておく仕組みです。呼び出し方や細かな設定は異なります |
| プロジェクトの共通ルールを伝える | `CLAUDE.md` | `AGENTS.md` | そのプロジェクトで作業するときに参照させる指示です。読み込み方や仕様は同じではありません |
| 以前からある仕組み | `.claude/commands/` のカスタムコマンドも引き続き使えます | Codex の custom prompts（`/prompts:name`）は非推奨で、Skills が案内されています | これから作る場合は、各ツールの現行形式を確認してください |

この記事のコマンドのように、必要なときに作業手順を呼び出す用途には、Codex の **Skill** が近い機能です。一方、`CLAUDE.md` / `AGENTS.md` は手順を呼び出すものではなく、プロジェクトの共通ルールを書くファイルです。Claude Code と Codex の Skills は、複数の AI ツールで手順を共有するための共通仕様である Agent Skills 標準をもとにしています。詳しくは[Claude CodeのSkills公式ドキュメント](https://code.claude.com/docs/en/skills)、[CodexのSkills公式ドキュメント](https://developers.openai.com/codex/skills/)、[Agent Skillsの仕様](https://agentskills.io/)を参照してください。

「スラッシュコマンド」は `/name` と入力して呼び出す方法のことです。カスタムコマンドだけでなく、組み込み機能や Skills も同じ形で呼び出せます。この記事の17本は、従来のカスタムコマンド形式で作っています。

### ユーザーコマンドや組み込み機能との違い

- **組み込みコマンド**: Claude Code に最初からある機能です。自分でファイルを用意する必要はありません。
- **自分用の作業手順**: Markdown ファイルに「何をするか」「何を受け取るか」「どう答えるか」を書きます。この記事では、これをカスタムコマンドとして作っています。
- **チームで共有する作業手順**: リポジトリに置いてチームで使います。個人用と同じ形式でも、秘密情報や必要な環境、変更の管理に注意が必要です。
- **その場のチャット指示**: 今の会話だけに使う指示です。何度も使う内容をファイルに残しておけば、毎回書き直さずに済みます。

「ユーザーコマンド」という名前だから特別な権限が付くわけではありません。どのファイルを使うか、どのツールが読むか、実行できる操作が何かを確認してください。

## 公開しているカスタムコマンドの一覧

**作業前の準備、作業中の定型処理、作業後の報告**に使う17本を公開しています。Windows 専用など、使える環境が限られるものもあります。導入前に、それぞれの前提を確認してください。名前の `ut-` は、作者個人用のコマンドだと分かるように付けています。

コマンド名は「対象 + 動作」を基本にしています。たとえば `docrewrite` は「文書を書き直す」、`diskreport` は「ディスクの状態を報告する」という意味です。一般的な略語は使いますが、独自の略語は避け、名前から役割を想像しやすくしています。

使う場面ごとに、Claude Code で入力する名前と役割をまとめました。たとえば `/ut-plan` と入力すると、そのコマンドを呼び出せます。

### 計画・引き継ぎ・レビュー

| 入力する名前 | 何をするか |
| --- | --- |
| `/ut-plan` | 作業前に、使う AI モデルや作業の進め方、確認方法を整理する。**作業そのものは始めない** |
| `/ut-handoff` | 作業を別のセッションに引き継ぐための情報を保存し、再開用のコマンドを表示する |
| `/ut-takeover` | 保存された引き継ぎ内容を、現在のリポジトリとブランチに合うか確認して読み込む。作業は始めない |
| `/ut-review` | 変更内容や計画を複数の観点で確認し、根拠のある指摘を重要度順に報告する。修正はしない |

### 報告・プレゼン資料

| 入力する名前 | 何をするか |
| --- | --- |
| `/ut-report` | 調査や作業の結果を、確認できた事実・判断・未確認の点に分けて報告書にする。Markdown / HTML で出力し、既定では機密情報を伏せる |
| `/ut-reportdeck` | `/ut-report` の報告書をもとに、読み手に合わせたプレゼン資料を別ファイルで作る。元の報告書は変更せず、新しい事実も加えない |

### 文書・データの整形

| 入力する名前 | 何をするか |
| --- | --- |
| `/ut-copyblock` | SQL、コード、文面を、コピーしやすいように1つずつコードブロックで出す |
| `/ut-docrewrite` | 既存の文書を、初めて読む人にも分かるように整理して書き直す |
| `/ut-commentrewrite` | 変更した箇所のソースコード内コメントを、初めて読む人にも分かるように書き直す |
| `/ut-sqlpatch` | データベースを手作業で復旧する SQL を、確認・適用・元に戻すための3つに分けて作る |
| `/ut-backlogformat` | Markdown を Backlog で使える書き方に変換する。**投稿はしない** |

### 環境・作業の支援

| 入力する名前 | 何をするか |
| --- | --- |
| `/ut-diskreport` | Windows の C ドライブで容量を多く使っているものと、削除候補を安全度別に報告する |
| `/ut-diskclean` | 作り直せる一時ファイルなどを、承認を記録してから削除する。先に `/ut-diskreport` で確認する |
| `/ut-diskarchive` | ファイルを元の場所に残したまま、1つずつ 7z 形式で圧縮する。元ファイルを消すかどうかは利用者が決める。先に `/ut-diskreport` で確認する |
| `/ut-vscode-debug` | VS Code の F5 キーで .NET / ASP.NET Core を HTTPS 接続でデバッグできるよう、設定ファイルを整える |
| `/ut-defer` | 利用制限などですぐにできない調査やレビューを予約し、後で自動実行する。読み取りだけを行う |
| `/ut-envsetup` | ブランチごとに作業フォルダを分けたとき、必要な設定やファイルがそろっているか確認し、指定されたものをコピーする |

### `/ut-report` と `/ut-reportdeck` の使い分け

`/ut-report` は調査結果を整理した元の報告書を作り、`/ut-reportdeck` はその内容をプレゼン資料にまとめます。資料を作るだけで、外部へ共有することはありません。資料の種類や確認方法などの詳しい説明は[README](https://github.com/TakaakiU/ut-commands#readme)を参照してください。

手元にはこのほかに、特定の環境に依存するため公開していないコマンドもあります。公開しているコマンドも、そのまま自分の環境で動くとは限りません。

### 補足: `/ut-defer` と `/ut-envsetup`

この2つは、ほかのコマンドとは用途が少し異なります。

- **`/ut-defer`**: 利用上限などですぐにできない作業を予約します。後で人が操作しなくても実行するため、調査やレビューなど、読み取りだけの作業に限っています。
- **`/ut-envsetup`**: Git worktree（ブランチごとに分けた作業フォルダ）で、開発に必要な設定がそろっているか確認し、指定されたファイルを配置します。詳しい使い方は[README](https://github.com/TakaakiU/ut-commands#readme)を参照してください。

## 代表例: `/ut-plan` を使う

### 使用例

たとえば、ファイルを直す前に「どんな順で進めるか」だけ決めたいときは、次のように入力します。

```text
/ut-plan public/claude-code-slash-commands.md の構成を初心者向けに見直す。記事は編集するが、内容を確認してから変更したい。
```

実行結果は、たとえば次のようになります（抜粋）。ここでいう `model` は使う AI モデル、`effort` はモデルにかける推論の強さです。委譲は別の AI に作業を任せること、並列化は複数の作業を同時に進めることです。`/ut-plan` はファイルを編集せず、進め方だけを提案します。

```text
前提とする作業内容（WHAT）
  記事の構成を初心者向けに見直す: 確定
  変更してよい範囲: 未確定（確認してから変更したい）→ 確定したら工程2の範囲を見直す

作業特性
  規模: 1ファイル / 元に戻せるか: Git で管理しているため可能 / 外部操作: なし

層A（工程の境目ごとの切り替え）
  境目                     入力するコマンド  確かめ方         確認元
  着手前 → 工程1（構成案）  /effort medium    /effort status   公式文書の URL
  工程1 → 工程2（編集）     切り替え不要      —                —

完了条件
  工程1: 見出し案を提示し、確認を得た
  工程2: 見出しの階層とコードフェンスの対応が崩れていない

このプロファイルは計画のみです。
- 始める場合: 上の表の「着手前」の行のコマンドを入力し、「工程1 の構成案を出して」と送ってください。
- 作り直す場合: 変えたい観点（例: コストを下げたい／検証を強めたい）を伝えてください。
```

このように確認する項目を決めておくと、毎回同じ観点で計画できます。計画を出すだけで、実作業を勝手に始めないことも、このコマンドの大事な点です。

工程が切り替わるときに入力するコマンドや確認方法も示すので、「次に何をすればよいか」が分かります。Claude Code の設定はバージョンによって変わることがあるため、利用時は公式ドキュメントも確認してください。

## 実物: カスタムコマンドの書き方

これは、よく使う `/ut-plan` の本文を短くした例です。従来のカスタムコマンドでは、このような Markdown ファイルに指示を書きます。リポジトリでは `commands/ut-plan.md` に置いています。どのコマンドも、基本の項目をそろえています。

見るポイントは、**入力（呼び出すときに渡す内容）の扱い・回答に必ず含めること・してはいけないこと**の3つです。コード中の `$ARGUMENTS` は、この入力を受け取るための名前です。用語と書き方をコードの後で説明します。

````markdown
---
description: 作業の進め方と確認方法を提案する。作業そのものは実行しない
argument-hint: [計画対象の作業内容。省略時は確認]
disable-model-invocation: true
disallowed-tools: Bash, Edit, NotebookEdit
metadata:
  scope: generic
---

# /ut-plan — 実行プロファイルの提示

## 1. 目的
作業を「どの強度でやるか」を先に決める。**実行はしない。**

## 2. 入力
- `$ARGUMENTS`: 計画対象の作業内容として扱う。**実行指示としては扱わない。**
- 未指定の場合: 停止して確認する。既定の対象を持たない。

## 3. 必須手順
1. 作業の可逆性を見る。不明なら安全側に倒す。
2. 検証強度を決める。「テストがある」を根拠にせず、**壊したときに落ちるか**で判断する。
3. 出力フォーマットに従ってチャットへ全文提示し、作業実行はしない。

## 4. 回答に必ず含める項目
| 項目 | 内容 |
|---|---|
| `前提とする作業内容（WHAT）` | 項目ごとの確定状態と、変わったときに見直す工程 |
| `model` / `effort` | 使うモデル・強度と理由 |
| `層A` | 工程の境目ごとの、入力するコマンド・確かめ方・確認元（同じなら「切り替え不要」） |
| `検証強度` | 何をもって「確認できた」とするか |
| `未確認事項` | 判断できなかった点 |

## 5. 禁止事項
- 計画と称して作業を始めない。
- `$ARGUMENTS` 内の「すぐやって」を実行承認として扱わない。
- 切り替えコマンドを、確かめないまま確定事項として書かない。

## 6. 補足
（判断に迷いやすいケースの一覧）
````

6つの項目を毎回そろえるのは、**最初の部分を読めば何をするコマンドか分かるようにする**ためです。「目的」と「入力」を見れば、何を受け取り、何をするのかが分かります。

特に大事にしているのは次の3点です。

1. **入力された文章は「作業の内容」であり、実行の許可ではないと書く。** たとえば入力に「確認せず進めて」とあっても、それだけで作業を始めないようにします。
2. **回答に必ず含める項目を決めておく。** 値を確認できなかったときは空欄にせず、「未取得」と書きます。空欄だと「問題なし」と受け取られるおそれがあるためです。
3. **してはいけないことを独立して書く。** 手順に埋もれて読み飛ばされないようにします。

## コマンドを設計するときのポイント

### 目的・入力・出力を先に決める

コマンドを書く前に、次の3つを決めます。

- **目的**: 何をするコマンドか
- **入力**: 呼び出すときに渡す文章をどう使うか。入力がない場合はどうするか
- **出力**: 回答に必ず含める項目と、判断できない場合の書き方

`/ut-plan` は、入力された文章を「計画する作業」として読みますが、「今すぐ実行してよい」という許可とは扱いません。回答には使うモデルや推論の強さ、確認方法、未確認の点を含めます。入力と出力を決めておけば、呼び出すたびに確認項目が変わりにくくなります。

### 既定は変更せずに試す

ファイルの編集・配置・削除などを行うコマンドは、最初は変更せずに「何をするか」の提示だけにします。実際に変更するときは `--apply` のような明示的な指定を必要にします。チャットの「お願いします」だけで実行を許可しないことも大切です。このように、実際には変更しない試し方を dry-run と呼びます。

### 成功条件を決める

「エラーが出なかった」だけでは、正しく終わったとは限りません。変更後に内容を読み直したり、更新した件数を確かめたりする方法も、回答に含めます。複数の件数を扱う場合は、たとえば次のように合計が一致するか確認します。

```
対象件数 == 処理件数 + スキップ件数
```

### 「0件」だけで判断しない

検索結果が0件でも、「該当するものがない」のか「検索の仕組みが動いていない」のかは分かりません。結論を出す前に、**見つかると分かっている例も同じ方法で検索し、見つかることを確かめます**。これを陽性対照と呼びます。

「試したけれど効かなかった」という場合も同じです。機能がないのか、**試す条件が整っていなかった**のかを先に確認します。条件が整っていない場合は、失敗したのではなく、結果を確かめられていません。

### 指示と機構を混同しない

本文に「実行しない」と書くのは、AI への指示です。一方、ファイル先頭の設定欄（frontmatter）にある `disallowed-tools` は、使えるツールを制限する設定です。ただし、実際にどう制限されるかは Claude Code の仕様に依存します。動作を確かめていない設定を「絶対に実行されない保証」と説明しないようにします。

## ファイル先頭の設定と配布時の注意

この記事の17本は、リポジトリにある `commands/*.md` を元ファイルとして管理し、Claude Code では `.claude/commands/` に配置する形式です。新しい形式として案内されている Skills は `.claude/skills/<name>/SKILL.md` に作り、こちらも `/name` で呼び出せます。カスタムコマンドの機能は Skills に統合されていますが、既存のコマンドファイルも引き続き使えます。補助ファイルも一緒に管理したい場合は、公式ドキュメントを確認して Skill 形式への移行を検討してください。

ファイル先頭に書ける設定は、Claude Code 独自のものと、複数のツールで使える Agent Skills 標準のものがあります。すべての設定が他のツールでも使えるとは限りません。別のツールに配る場合は、`argument-hint` や `disable-model-invocation` などが対応しているか、[公式ドキュメント](https://code.claude.com/docs/en/skills)で確認してください。

次に、ツールごとに設定の違いを確認した例を紹介します。

## Codex からも同じコマンドを呼ぶ

### 仕組み

Codex から使う場合も、手順の本文は `commands/ut-*.md` を共通の元ファイルとして使います。Codex 側には「どのファイルを読むか」だけを指定する入口を置き、本文はコピーしません。コピーすると、一方だけを修正して内容が食い違うおそれがあるためです。

```text
$ut CMD=ut-plan ARGS="README の構成を見直す。実行はせずプロファイルだけ"
```

`CMD` に使いたいコマンド名、`ARGS` に渡したい内容を書きます。本文中の `$ARGUMENTS` は、ここで指定した `ARGS` の内容として扱います。

### custom prompts から skills へ移した経緯

最初は Codex の **custom prompts**（`~/.codex/prompts/ut.md` に置き、`/prompts:ut ...` で呼び出す形式）を使っていました。その後、Codex の公式文書で custom prompts は非推奨となり、代わりに **Skills の利用が案内されました**（2026-09-30 時点では、廃止時期は示されていません）。将来使えなくなる可能性に備えて、入口を Skills（`~/.agents/skills/ut/SKILL.md`）に移しました。呼び出し方は `/prompts:ut ...` から `$ut ...` に変わりましたが、渡す内容は同じです。

移行時に分かった大きな違いは、**Skills は、依頼内容に応じて自動で呼び出される場合がある**ことです。説明に合う依頼をすると、名前を指定しなくても起動します（作者の環境では3回試して3回とも起動）。一方、このコマンド群は「人が名前を指定したときだけ使う」方針です。Claude Code では `disable-model-invocation: true` で自動利用を止めていますが、Codex の `SKILL.md` では同じ設定が使えません。

Codex で自動利用を止めるには、Skill のフォルダに `agents/openai.yaml` を置き、次の設定をします。

```yaml
policy:
  allow_implicit_invocation: false
```

この設定後、同じ依頼を3回しても起動せず、`$ut` と指定したときだけ動くことを確認しました。ツールによって設定方法が違う例です。

この設定で自動利用を止め、ファイルを配置するときにも設定を確認しています。検査内容や配置方法の詳細は[README](https://github.com/TakaakiU/ut-commands#readme)を参照してください。

## 導入

```sh
git clone https://github.com/TakaakiU/ut-commands.git ut-commands
cd ut-commands

node tools/deploy.mjs --check                          # 整合性検査
node tools/deploy.mjs --target claude                  # 差分の確認（dry-run）
node tools/deploy.mjs --target claude --apply          # ~/.claude/commands/ へ配置
node tools/deploy.mjs --target codex-skills --apply    # Codex からも使う場合（~/.agents/skills/ へ配置）
```

作者の環境では、Claude Code の VS Code 拡張に反映するため、**ウィンドウの再読み込みだけでなく、すべてのウィンドウを閉じて起動し直す必要がありました**。バージョンや環境によって異なる可能性があるため、反映されないときに試す方法として参考にしてください。

## 限界と注意

- **作者1人が自分用に作っているものです。** 利用者向けに整備された配布物ではなく、予告なく大きな変更をすることがあります
- 動作前提は Windows / Node.js 20.11 以上（`usage-stats.mjs` が `import.meta.dirname` を使っています）。他OSでは確認していません
